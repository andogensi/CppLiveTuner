# セキュリティと移行ガイド

LiveTunerは利用アプリと同じプロセス内で動作します。設定ファイルを編集できる人は、
アプリの動作を変更できる運用者として扱ってください。認証・承認機構は提供しません。

- 通常のローカル開発では、設定とリンク先を信頼できるプロジェクトファイルとして扱います。
  ビルドディレクトリから設定をリンクする構成も既定で読み取り可能です。
  ファイルの自動作成と、リンク経由の保存は引き続き行いません。
- 最終要素のsymlink/reparse pointを拒否する必要がある運用では、全翻訳単位で
  `LIVETUNER_STRICT_FILE_READS=1` を指定します。これは任意の厳格設定です。
  ローカル開発だけなら、下記のサービス向け認証・承認基盤までは要求しません。
- サービス運用では固定の絶対パスを使い、すべての親ディレクトリと許可したリンク先を
  ACL・所有者設定で保護してください。厳格設定も、書き換え可能な親ディレクトリや
  ネットワークファイルシステムを安全な境界に変えるものではありません。
- 本番で変更を禁止する場合は、全翻訳単位で `LIVETUNER_ENABLE_RUNTIME=0` を指定します。
  読み取り・監視・nlohmannの保存が無効になり、bind時の既定値は利用できます。
  既存の開発用途との互換性のため、既定値は `1` です。
- 業務上の値域・項目間制約、変更者の認証、承認、監査ログ保持、世代別ロールバックは
  利用アプリ側で実装してください。

Windowsの既定の読み取りは通常のreparse処理に従い、属性だけで一律拒否しません。
OneDrive実環境での同期・取得は未検証です。厳格設定や明示的な保存はプレースホルダーを
拒否する可能性があります。また、再試行のsleepをしなくてもOS・クラウドのI/Oは待機し得るため、
フレーム時間が重要な設定はローカルファイルに置いてください。

## 互換性変更

読み取りAPIはファイルを自動作成しません。信頼できるセットアップ処理で事前に作成してください。
存在しないファイルはエラーとなり、待機APIは有効な内容を待ちます。JSONのコメントや後続ゴミは
認めません。nlohmannの空ファイルを空オブジェクトとして扱う挙動は維持しています。

`NlohmannParams::save()` は既存の通常ファイルだけに書き込み、symlink/reparse point・
hard link・存在しないファイルは拒否します。開いたハンドルを検証してから切り詰めますが、
クラッシュ時のトランザクション保証はありません。必要なら運用側で原子的な置換を行ってください。

読み込みは実データ1 MiB、JSONの入れ子は64階層、項目・構造要素は4096、キーは1024バイト、
値は64 KiBに制限します。JSONのエスケープや入れ子のコンテナも予算を消費します。
数値オーバーフローや非有限値を拒否し、不正な設定では直前の正常な値を維持します。
独自型の抽出・代入演算子の安全性は利用アプリの責任です。
nlohmannの数値型変換でも値域を検証し、vector・array・文字列キーのmap内にも適用します。
表現可能な小数から整数への切り捨ては維持します。独自型・その他のコンテナへの変換は
利用アプリ側でも値域を検証してください。

非同期APIは呼び出し時のパスと設定を保持し、後からの `set_file()` は次の操作に適用されます。
未完了の処理はmove先へ移動します。破棄・`reset()` はキャンセルしてワーカー終了を待ちます。
キャンセルされたfutureは `AsyncCancelled` を投げ、未実行のコールバックは呼びません。
非同期処理は所有者の `last_error()` を書き換えません。futureの例外または診断ログを使います。
LiveTunerのコールバックから所有者を破棄する場合、現在のワーカーだけは独立した状態で終了します。
コールバックが参照する外部変数の寿命は、呼び出し側で管理してください。

Paramsの変更通知は引き続き `update()` / `poll()` の呼び出しスレッドで実行します。
監視中のParamsをmoveしても通知を引き継ぎます。内部FileWatcher自体はmoveできません。
オブジェクトの破棄・moveと外部のメンバー呼び出しを競合させず、Paramsの変更コールバックから
自分自身を破棄・moveしないでください。bind先の変数への別スレッドからのアクセスにも同期が必要です。

Loggerと設定・エラーのgetterはコピーを返します。Logger変更には `set_log_callback()` を使います。
診断コールバックはインスタンスのロック解放後に実行し、ログの制御文字をエスケープ・長さ制限します。
再帰ログは抑止します。遅延診断コールバックの例外は既定の診断出力へ報告します。
生のErrorInfoをアプリ側でログへ出す場合は、その出力側でもエスケープしてください。

## 検証と運用

CMake 3.20以上を使い、`LIVETUNER_IMPLEMENTATION` は1つの翻訳単位に定義します。
`LIVETUNER_TEST_OPTIONAL_BACKENDS=ON` でハッシュ固定済みの外部JSON依存を取得します。

```sh
cmake -S . -B build -DLIVETUNER_BUILD_TESTS=ON -DLIVETUNER_TEST_OPTIONAL_BACKENDS=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure --no-tests=error
```

CIはWindows/Linux/macOS、Debug/Release、組み込み/64bit整数/外部picojson/nlohmann、
ASan/UBSan、TSan、fuzz、複数翻訳単位、インストール後の利用を検証します。
テスト件数ゼロ・タイムアウト・サニタイザーエラーも失敗になります。

リポジトリ管理者は `Required CI` を必須チェックに指定し、既定ブランチへの直接pushや迂回を
制限してください。このPRのworkflowだけでGitHub側の保護設定は変更されません。
リリース署名、SBOM/provenance、脆弱性対応の責任者・手順は組織として別途整備が必要です。
